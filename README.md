# 自动调研 Agent

给定一个研究主题，Agent自主完成【搜索→筛选→阅读→成文】,产出一份带可核验出处的调研报告。

## 效果

10个主题的评测结果：

| 指标 | 结果 |
|---|---|
| 任务成功率 | 10 / 10 |
| 平均步数 | 8.3 步 |
| 平均耗时 | 38.9 秒 |
| 单篇引用数 | 10 ~ 30 条 |

成功率判定标准：产出报告>=300字、引用>=5条、分节>=3个、不以“资料不足”收尾。
**这是格式合规率，不是内容正确率**——内容真实性靠人工抽查（已抽2处，均与原文一致）。

## 架构

```
主题
->拆2~3个关键词方向，分别search_web
->三道筛：相关性≥1.5、来源权威≥3、时效180天内
->search_web只返回600字摘要，供模型判断相关性
->模型判断值得细读的，调read_page取正文（单次2000字，可翻页）
->循环，直到模型认为资料足够
->生成markdown报告，论断后标 [编号]
->rebuild_refs用报告正文编号重建来源列表
```

## 关键设计

### 1.两档取材，而不是一次全塞
‘search_web’只返回摘要（约600字），‘read_page’才返回正文（2000字/次，带‘start’翻页）。
实测一个主题3次搜索、12次读页，累积约2万字。如果搜索时就把正文全带上，同样的信息要6-8万字

### 2.引用列表由程序生成，不由模型生成
模型写正文时标‘[编号]’，但列来源列表时会自己从1重排，导致正文如【21】在列表里找不到。
修法：函数rebuild_refs从正文按出现顺序提取编号，查POOL取url，重新生成列表。模型编造的编号（超出池子范围）单独标记为“来源不存在”。
**这是用代码保证一致性，不靠提示词约束模型。**

### 3.每次run重置编号池
POOL和_next_idx是模块级全局变量。批量测评时如果不重置，编号会跨主体累积。
更危险的是：模型编造的编号可能**恰好撞上上一个主题的编号**，从而配上一个真实但完全无关的URL——这种错误永远查不出来。


## 踩过的坑

| 问题 | 现象 | 根因 |
|---|---|---|
| 参数校验错 | `search_web() got an unexpected keyword argument 'idx'` | `TOOLS` 里 `required` 写成 `["idx"]`，正确应为 `["query"]` |
| 编号跨主题累积 | 第 8 个主题的引用编号到 176 | `_next_idx` 未重置 |
| 正文与列表编号不一致 | 正文 `[21]`，列表只有 18 条 | 模型自己重排列表，用程序重建解决 |
| 引用幻觉 | 正文出现 `[32]`，但池子只有 24 条 | 模型自行编号，由 `rebuild_refs` 标记为缺失 |

## 局限
- **无缓存**：同一 URL 在多次主题评测中会被重复请求，未做本地缓存
- **无成本统计**：未记录每次调用的 token 消耗
- **内容真实性依赖人工抽查**：程序只能保证"编号对得上"，不能保证"URL 里真有那句话"


## 文件

| 文件 | 作用 |
|---|---|
| `agent.py` | 主流程：工具定义 + Agent 循环 |
| `filter_demo.py` | 搜索层：接口调用 + 三道筛 |
| `refs.py` | 引用重排：从正文编号重建来源列表 |
| `eval.py` | 批量评测 10 个主题 |
| `check.py` | 验证引用完整性 |
| `reports/` | 各主题生成的报告 |

## 运行

```bash
pip install requests
set DEEPSEEK_API_KEY=sk-...

python agent.py    # 跑单个主题
python eval.py     # 批量评测 10 个主题
python check.py    # 验证引用完整性
```
