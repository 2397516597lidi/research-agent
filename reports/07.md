# MCP（模型上下文协议）采用现状与企业实践调研报告

> 说明：本报告仅基于检索到的公开资料整理，数据截至 2026 年 11 月前后；不同来源的统计口径差异较大，报告已在相应位置标注。

## 一、生态规模：从“一个开源协议”变成事实标准

MCP 由 Anthropic 于 2024 年 11 月开源，随后在 2025 年 12 月被捐赠给 Linux 基金会下的 Agentic AI Foundation（AAIF，由 OpenAI、Block 共同创立，Google、微软、AWS、Cloudflare、Bloomberg 等支持）[13][23]。这一“中立化”动作被视为其从单厂商协议走向行业基础设施的转折点。

规模数据呈现出极强的量级跃升：

- 公开 MCP 服务器数量已超过 2 万个：MCP.so 目录收录 21,000+，Glama.ai 列出 23,000+；这两者都只统计公开服务器，不含企业内部服务器，因此实际总量更高 [10]。另有统计称 3 月时各类注册表已索引 16,000+ 个服务器 [23]。
- 下载量：官方 TypeScript SDK 的月下载量从 2025 年 2 月的 35.1 万次增长到 2026 年 10 月的 4.59 亿次 [12]；2026 年 4 月本地 MCP 服务器下载约 6,700 万次/月，每周总浏览量约 1,800 万次 [10]。
- 一项学术测量研究采集了六大市场 8,401 个有效 MCP 项目、341 个有效客户端做实证分析，是该领域首个大规模生态测量 [11]。
- 客户端侧已被主流工具吸收：ChatGPT、Cursor、Claude、Gemini、Microsoft Copilot、VS Code 等均已支持 [23]。

值得注意的是“声量与装机量背离”：2026 年上半年社区出现大量“MCP 已死、直接用 CLI”的论调（Karpathy 称 CLI 令人兴奋、Google Workspace CLI 取消 MCP 模式），但同月 SDK 下载量翻倍；到 2026 年 8-11 月，Apple、Vercel、Paper 相继发布 MCP 功能，争论焦点从“要不要用 MCP”转向“谁能接入” [12]。

## 二、企业采用的真实成色：41% 的“生产环境”需要打折看

关于企业采用率，最有价值的是一组能互相印证、但结论偏冷的调研数据：

- Stacklok 与 AAIF 合作、2026 年 7 月对 100 名美英企业资深软件工程师的调查显示：41% 的受访者称已有 MCP 在生产环境，但拆开看，86% 的 MCP 使用仍处于实验或本地开发阶段，只有 5% 属于“受治理的企业级生产环境”，另有 9% 虽在生产但基本无治理 [24]。报告直言“生产环境”与“受治理的生产环境”之间的鸿沟是当前的核心矛盾。
- Clutch Security 的研究更为直观：86% 的 MCP 服务器跑在开发者本机上，只有 5% 运行在 CI 管道、云负载、Kubernetes 等生产环境；在一家万人规模企业中，约 1,500 名员工人均运行 2 个 MCP 服务器，形成 3,000+ 个部署、连接 115 个不同企业服务，且“几乎全部是本地部署” [23]。
- 生态增速与生产成熟度严重不匹配：13 个月内实现约 2,200% 增长（2024 年 10 月 3 个实现 → 2025 年 11 月近 7,000 个），但“几乎没有一个是生产级的” [23]。
- Zuplo 2026 年初的 State of MCP 报告（近 100 位技术负责人）显示：72% 预计未来 12 个月 MCP 使用量会增加；58% 的 MCP 构建者只是把现有 API 包装成 MCP；多数用户配置 2-7 个服务器；63% 的用户用 MCP 同步文档、知识库等数据源 [10]。另有 38% 的构建者表示安全顾虑正在阻碍其扩大采用 [23]。
- 成熟度定位：Gartner 已将 MCP 置于“失望低谷”（Trough of Disillusionment）[24]。

也就是说，MCP 的“协议问题”基本解决，“组织与运维问题”才刚刚开始——这与容器技术 2014 年前后的阶段被直接类比 [23]。

## 三、安全与治理：从“能调工具”到“被治理地调工具”

安全已成为企业落地的首要约束，而非协议设计本身 [24]。49% 的受访者将安全与合规列为 MCP 实施第一大挑战，34% 提到治理 [24]。

公开研究揭示的服务器侧风险相当集中：

- Equixly 2025 年测试发现 43% 的 MCP 服务器存在命令注入漏洞；22% 允许读取预期目录之外的文件；30% 允许无限制的 URL 抓取 [10]。
- Astrix 分析 5,200+ 个开源 MCP 服务器实现：88% 需要凭据才能运行，但 53% 依赖长期有效的静态密钥（API Key、PAT），仅约 8.5% 使用 OAuth [10][23]。
- Bloomberry 对 1,400 个服务器的分析中，在能判定鉴权方式的部分，38.7% 完全没有鉴权 [10]。
- 2026 年 4 月披露的设计弱点中，研究者演示了通过 MCP 工具调用实现任意命令执行 [24]。
- NSA 于 2026 年 5 月发布 MCP 安全设计指南，明确指出协议本身不自动提供安全边界，序列化风险、信任边界模糊、Agent 滥用是核心关切 [19]。

另一类常被低估的成本是“上下文膨胀”：有开发者实测在尚未开始有效对话前，MCP 工具定义就占了 Claude Code 20 万 token 上下文窗口的 16.3%；而 Anthropic 给出的“用代码执行替代直接工具调用”方案，在一个 Google Drive→Salesforce 的示例中把 token 从 15 万降到 2,000（约 98.7% 的成本节省）[10]。

治理层面的共识正在形成：MCP 把 Host→Client→stdio/Streamable HTTP→Server→第三方系统的接入标准化了，但并不自带授权、风控与审计，必须在每次调用前做身份透传、RBAC 与参数契约校验 [14]。责任需要分层：工具层保证“工具本身不作恶”（输入校验、最小权限、高危操作二次确认）；Agent 层保证“工具不被误用”（工具级 RBAC、阈值人工确认、异常高频告警、工具返回内容进上下文前过滤）；平台层保证“链路安全”（传输加密、工具注册审核、跨工具数据流审计）[15][16]。

## 四、企业落地的主流形态：MCP 网关 + 语义层/注册表

从 2026 年下半年的多篇架构文章看，企业实践正快速收敛到“不要让 Agent 直连内部系统”的模式。

**MCP 网关**位于 MCP 客户端与 MCP 服务器之间，对客户端表现为一个聚合的 MCP 服务器，对后端则是 MCP 客户端；它回答四个固定问题：谁在调用、以谁的身份、能做什么、做了什么 [13][19]。治理的技术落点很具体：在 `tools/list` 阶段按当前身份过滤可见工具，在 `tools/call` 阶段做参数校验、授权判定与审计落库 [13][19]。这意味着网关不是普通反向代理，它必须理解 MCP 的工具语义 [19]。

工具接入通常有三种方式，其中两种被重点描述：把只提供 stdio 的开源服务器放进容器统一托管、再由网关以 Streamable HTTP 对外暴露（凭据从员工本机转移到网关密钥管理）；以及对已是 Streamable HTTP 的服务器（含 SaaS 厂商的远程 MCP 服务器）做反向代理 [13]。在鉴权上，实践建议显式禁止把 Token 原样转发下游，改用 OAuth 2.1 + PKCE 或通过企业托管授权（EMA）兑换令牌，并在网关的 `tools/list`、`tools/call` 两处卡权限 [17]。也有观点强调按业务边界拆分 Server、把公共鉴权、日志与配额放到统一网关，避免“万能 Server” [14]。

**架构分工**上，一种被明确推荐的划分是：工具注册发现归注册表，权限治理与调用安全归网关，多模型适配归协议层，业务系统对接归各域 MCP Server；并建议直接按 2025-06-18 版规范设计，尤其要利用结构化工具输出（声明输入/输出 schema，网关拒绝无 schema 的工具上线）与 Elicitation（服务端反向请求）[20]。

**传输层**现状：Bloomberry 数据显示 93% 的 MCP 服务器已使用 Streamable HTTP，7% 仍用已弃用的 SSE [10]；而更早的学术测量（341 个客户端）显示 SSE 占 56.98%、stdio 占 38.12%、其他 4.99%，说明生态当时仍处过渡期 [11]。生产化的关键坎在于从 STDIO 切到 HTTP：安全面从零突增到需要 OAuth、Token 管理、CORS、TLS、重定向校验、SSRF 防护、限流与审计日志；Stacklok 的压测显示 STDIO 在 20 个并发连接下 22 个请求中有 20 个失败，因此“大规模下无法停留在本地” [23]。

## 五、行业实践案例：先行者已经跑出可量化收益

**数据/金融信息服务：S&P Global Energy。** 其做法是把“语义层”和“协议契约”分离：由领域专家为每个数据集组策划一个 Genie Agent（不写 Agent 代码），形成受治理的语义层；这些 Genie Agent 作为托管的 MCP 服务器，通过 FastMCP 代理组合成跨域查询的复合端点，同时保留 Unity Catalog 的治理能力，显著缩短了对话式数据产品的上市时间 [4]。

**大型机构自建：Bloomberg 与 JPMorgan。** Bloomberg 2026 年 7 月披露其 9,500 人的工程团队借助 MCP 把 Agent 上下文配置时间从数周缩短到数分钟；JPMorgan Chase 披露有 450+ 个 Agent 用例在生产运行，许多构建于 MCP 兼容工具之上——但报告同时提醒，这属于有一流 AI 基础设施团队与预算的一线机构，不代表中位数企业 [24]。

**内部效率：Workato。** 1,000 名员工获得 Claude for Business 后原本每天只有 150-200 次对话；接入只读 MCP 服务器后使用量增长 700%，达到每天约 1,000 次；CIO 称内部 Agent 已带来 270 万美元新销售机会 [10]。

**中国企业的两个样本：**
- 海尔盈康一生基于阿里云 RDS Supabase 构建 AI 原生应用平台，业务人员用自然语言开发应用，再通过 MCP、Skill 等方式把应用接入智能体，使其参与具体业务流程；已落地 451 个应用，覆盖模具管理、3D 演示等一线场景 [2]。
- 科达自控面向智慧矿山自研大语言模型服务平台，基于 Spring AI 1.1.x + Spring Boot 3.5.x，对接 20 余个 MCP 人员定位接口以及安全监测、机电设备、生产调度等业务域接口，覆盖实时统计、人员轨迹、下井记录、报警分析等场景 [5]。

**存量系统改造思路**：Spring Boot + MCP 的典型路径是不重构原系统，而是在外层做适配层，把业务方法封装为 AI 可识别的工具；文中明确指出 STDIO 仅适合本地单场景调试，企业多客户端、远程访问场景应选 SSE 模式（体现的仍是较早期的传输选型认知）[3]。Oracle CPQ 场景中，Argano 构建 MCP Server 把原本需要数小时、跨配置/商业逻辑/数据表/性能日志排查的问题转成对话式查询 [8]。

**受监管行业仍偏谨慎。** 有报道指出，尽管 MCP 用户数快速增长，银行等金融机构对 MCP 与 A2A 类开放智能体交换的采用相对保守 [1]。在受监管工作流中，MCP 驱动的流程可能包含多个未预先定义的运行时决策，组织必须能证明“谁发起、访问了什么数据、执行了什么动作、有何证据支撑结果”，这构成了若干治理断点 [21]。

## 六、结论与资料局限

1. **协议层已经胜出，部署层仍是早期。** MCP 完成了架构锁定与中立化治理，生态规模（2 万+ 公开服务器、数亿级 SDK 月下载）和客户端覆盖都指向事实标准 [10][12][13][23]；但企业侧“受治理的生产环境”仅约 5%，绝大多数仍是本地实验 [23][24]。
2. **瓶颈是安全与组织，不是协议。** 静态密钥、缺鉴权、命令注入、上下文膨胀等问题在公开研究中反复出现 [10][23]，而 NSA 指南与网关方案基本给出了方向性答案 [13][19]。
3. **落地形态趋于统一：网关 + 注册表 + 语义层，分层担责。** [13][19][20]
4. **收益已在头部企业可量化**（配置时间、对话量、销售机会、应用数量）[2][10][24]，但样本集中于有专门 AI 平台团队的机构，中位数企业的路径“更慢、更乱、更贵” [24]。

**公开资料有限之处：**（1）缺少按行业、按企业规模分层的系统性采用率统计，现有 41%/5% 等数字来自 100 人规模的问卷与安全厂商的扫描样本，代表性有限 [23][24]；（2）企业内部 MCP 服务器总数无可靠公开数据，只能由“公开目录数 + 万人企业约 3,000 个部署”做粗略外推 [10][23]；（3）中国企业案例多为厂商或客户的单方分享，缺少第三方效果验证 [2][5]；（4）受监管行业（金融、医疗）的落地细节公开信息很少，本报告只能给出方向性判断 [1][21]。
