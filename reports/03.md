# AI Agent 记忆机制主流技术方案对比

## 一、问题起点：为什么"接个向量库"不构成记忆方案

LLM 推理本身是无状态的——模型只能看到当前上下文窗口里的 token，因此凡是需要跨轮次、跨会话保留的信息，都必须依赖外部的存储与检索层 [7]。在长时程（long-horizon）任务中，上下文窗口的硬性限制使外部记忆系统成为刚性需求 [8]。

但业界最常犯的错误正是"把会话原样倒进向量库"。工程实践中的反馈很直接：向量检索能翻出你上个月说过的那句话，却不记得你已经否决过的方案；能检索到"预算 50 万"，却不知道这个数字后来改成了 30 万——**向量检索擅长"找回原话"，不擅长"记住结论"** [2]。学术综述也记录了同一转向：2024–2025 年记忆架构从简单的向量存储快速迭代到复杂的神经-符号混合系统，早期纯向量相似度检索在复杂推理与多跳查询上表现不佳，难以维持信息间的逻辑关联 [8]。

因此，判断"是否是长期记忆"不能看它是否已落库。一个已持久化的会话历史，仍可能只是"线程级短期记忆"；真正的长期记忆通常需满足：能跨会话复用、有明确作用域（用户/项目/组织/Agent）、经过提炼而非原始对话堆积、带来源置信度与时间语义、支持更新/冲突处理/过期/删除/审计、可按需召回、且不会覆盖更高优先级的系统策略与安全规则 [1]。

## 二、分层模型：从"三层"到"七层"

最常见的入门划分是三层：短期记忆（上下文窗口里的近期对话与工具结果）、工作记忆（Agent 主动维护的当前任务状态"白板"）、长期记忆（躺在外部存储里的偏好、事件与教训）[4]。也有资料按"工作记忆 / 情景记忆 / 知识记忆"三分，并指出**大多数"Agent 记不住"的问题其实是情景记忆缺失——它没有记录"用户否决了什么"，而不是知识检索不够** [2]。

更贴近工程的模型不止两层。一份 2026 年的工程长文给出七层划分 [1]：

| 层级 | 主要内容 | 常见实现 | 生命周期 |
|---|---|---|---|
| 感知与事件层 | 用户消息、工具调用与结果、外部事件 | Event Log、Message Store | 长期留存或按策略归档 |
| 工作记忆 | 当前目标、计划、最近消息、临时变量 | Context Window、Graph State、Scratchpad | 当前任务/会话 |
| 会话记忆 | 完整线程历史、阶段摘要 | Session Store、Checkpoint | 单会话或短期恢复 |
| 语义记忆 | 用户偏好、稳定事实、实体关系 | Profile、JSON、向量库、知识图谱 | 中长期 |
| 情景记忆 | 某次任务发生了什么、结果如何 | Episode、Trajectory、Session Summary | 中长期 |
| 程序记忆 | 如何完成某类任务、流程、策略 | Skill、Runbook、Prompt、Workflow | 长期，需版本化 |
| 权威规则 | 安全策略、组织规范、硬约束 | Policy、Config、AGENTS.md/CLAUDE.md | 长期，不可被普通记忆覆盖 |

这七层与经典 CoALA 四分类（语义/情景/程序 + 工作记忆）一脉相承 [1]。关键区分是**语义记忆"知道什么"、情景记忆"发生过什么"、程序记忆"如何做"** [1]；三者在"是否可直接执行"上还有递进——情景记忆不直接可执行，程序记忆不一定可执行，只有 Skill 是"在明确条件下可稳定执行" [3]。

还有一个必须分清的三元组：**状态**（"任务完成 60%"）应进任务数据库或状态机；**规则**（"生产环境禁止自动删库"）应进配置/策略；只有通过交互学到且值得复用的信息才属于**记忆** [1]。把三者混在一个向量库里，是记忆系统失败的主要根源之一。

## 三、主流技术路线对比

按存储形态与组织方式，可归为以下几类，它们并非互斥，生产系统常做组合。

**路线 A：全量上下文（最朴素，也最被低估）。** 把历史全部塞进窗口。成本随轮次线性增长，长任务会爆 token，但优点是"零检索误差"——在 50 轮以内的任务里往往比任何 RAG 方案都准。所以第一步不该是上向量库，而是先回答：这个任务真的需要跨会话记忆吗 [2]。OpenAI 的 ChatGPT 记忆就是这条思路的工业化版本：四层上下文窗口注入（保存的记忆、聊天历史综合、会话元数据、当前上下文），周期性地做后台综合后整块注入，**没有向量库、没有图**，比外界想象得简单 [9]。

**路线 B：压缩摘要。** 每 N 轮把对话压成一段摘要替换原始记录，是成本最低的折中 [2]。

**路线 C：结构化情景记忆。** 不存原文，存"结论 + 状态"，用一张表或 JSON 文件记录 facts/decisions，并强制带时间戳。关键设计是**决策类信息必须带时间戳并允许覆盖**——向量库做不到"这条作废"，结构化记录可以 [2]。

**路线 D：向量库 + LLM"抽取—更新"流水线。** 代表是 Mem0（arXiv:2504.19413）：两阶段 LLM 流水线，先从消息对与摘要/近期上下文中抽取显著事实，再逐条与语义相似的已有记忆做 `ADD`/`UPDATE`/`DELETE`/`NOOP` 对账；底座是向量库中的稠密嵌入，图变体 Mem0^g 在 Neo4j 上构建有向标注图 `G=(V,E,L)` 并做逐实体嵌入 [10]。它被定位为跨框架的"记忆中间件" [3]。

**路线 E：时态知识图谱。** 代表是 Zep / Graphiti（arXiv:2501.13956）：把非结构化对话与结构化业务数据融合，边上**双时态**（事件时间 `valid_at` + 摄入时间 `invalid_at`），并做实体、关系、社区聚类与多层摘要；检索为语义 + BM25 + 图遍历的混合模式 [9][10]。其价值在于区分"知道状态"与"知道状态随时间如何变化" [9]。

**路线 F：OS 式分层 + Agent 自管理（MemGPT / Letta）。** 把上下文当虚拟内存管理："主上下文"类比 RAM、"外部上下文"类比磁盘，Agent 通过自己生成的函数调用**自我编辑**记忆 [10]。分层为 Core memory（固定大小、常驻上下文、不驱逐）、Archival memory（追加式向量存储、按需检索）、Recall memory（对话历史、可向量检索）[9]。2025 年引入的"睡眠时计算"（arXiv 2504.13171）让 Agent 在空闲时异步整理、重组和预计算记忆，被评价为"最高杠杆的架构思想"之一；同时把记忆管理 Agent 与对话 Agent 分离，避免相互干扰 [9]。同类的 MemOS 把记忆当作 OS 抽象层（Fact / Experience / Working memory 多存储统一 API）[9]。其代价是：需要严格的工具权限与安全策略，Agent 可能错误修改自身记忆，多 Agent 共享时治理难度高 [3]。

**路线 G：链接式笔记网络。** A-Mem 受 Zettelkasten 启发，Agent 为每条记忆生成上下文描述、关键词与标签，并按相似度建链，形成会演化的笔记网络；新记忆会触发对既有记忆的更新 [9]。在统一框架的视角下，这类方法的机制是"连接相关经验"——用图结构边或记录间关联链，让 A-MEM、MemoryOS 支持同步更新与对齐 [5]。

**路线 H：框架/平台托管记忆。** 一方提供会话持久层与提取策略，应用层很少自己造：

| 系统 | 短期记忆 | 如何进入长期记忆 | 主要特点 |
|---|---|---|---|
| OpenAI Agents SDK | Session 保存会话历史 | 跨线程长期记忆通常由应用层另建 Store | 更偏 Agent Loop 的会话持久层 |
| LangGraph / LangMem | Thread State + Checkpointer | Agent 主动写入或后台自动提取 | Namespace、Profile、Collection、Episode、Procedural 模式较完整 |
| Google ADK / Memory Bank | Session 和 State | `add_session_to_memory`、事件写入或托管提取 | Session Service 与 Memory Service 分离 |
| AWS AgentCore Memory | 原始会话事件 | 按语义、偏好、摘要、情景 Strategy 异步提取 | 强调托管策略、namespace |
| Microsoft Foundry Memory | 由 Agent 框架维护 | 平台执行提取、合并与冲突处理 | 支持 Profile、Summary、Procedural、TTL 与 CRUD |
| Mem0 | 应用提交对话消息 | `add` 提取原子事实并去重索引 | 适合做跨框架 Memory Middleware |
| Zep / Graphiti | 会话与业务数据作为 Episode | 增量构建实体、关系、带时间的事实 | 时态知识图谱 + 混合检索 |
| Letta | 当前上下文、消息、工具调用 | Agent 通过 Memory Tools 自管 | Core / Recall / Archival 分层 |
| CrewAI | Agent、Crew、Flow 运行上下文 | Memory API 或文本提取原子记忆 | 语义、时间、重要性综合召回 |

（据 [3]）

**横向能力对照**（不同来源的评测/描述口径不一，仅供定位）：Letta 强在 Agent 驱动的记忆控制，Zep 强在时序推理，Mem0 强在生态广度，Hindsight 强在检索准确率（多策略并行：语义 / BM25 / 图 / 时间 + 交叉编码器重排，写入时做实体消解与事实抽取）；报告明确指出**目前没有系统同时具备全部最佳实践** [9]。此外还有 SuperMemory（记忆+RAG+画像+连接器，闭源）、Mastra 的 Observational Memory（基于日志、上下文稳定因而可命中 prompt cache，牺牲新鲜度换延迟可预测）等路线 [9]。

## 四、写入与维护：真正的工程难点在"记忆编译"

共识正在形成：短期记忆进入长期记忆不是复制粘贴，而是一套受控流水线——会话事件 → 候选记忆提取 → 类型识别 → 作用域判断 → 价值评分 → 证据校验 → 去重与冲突处理 → 持久化 → 建立索引 → 按需召回 [1]。上游的抽取-对账循环在 Mem0、Zep、Letta 等系统中高度相似，差别主要在后端形态（向量嵌入 / 时态知识图谱 / OS 式分层上下文）[10]。

**触发时机**：用户明确说"请记住/更正/忘记"、会话结束、长时间空闲、上下文即将压缩前、任务完成并通过验证、定时后台 Consolidation、相似成功或失败模式反复出现、用户正负反馈 [1]。

**原子化**：不要直接保存长摘要，应拆成独立、可更新、可验证的原子事实——单条更易更新、冲突处理更准确、可分别设作用域与有效期、检索命中更精准 [1]。

**冲突处理**：写入前必须先检索已有记忆，做去重、实体对齐、同义归一、冲突检测、时间区间调整、权威等级比较与新老版本关联，最终落到五种动作之一：`ADD` / `UPDATE` / `SUPERSEDE`（新事实取代旧事实）/ `INVALIDATE`（事实失效）/ `NOOP` [1]（与 Mem0 的四动作设计同构 [10]）。

**晋升打分**：一种可落地的示例公式为 `P = 0.25E + 0.25U + 0.15S + 0.15C + 0.10R + 0.10N − Risk − Conflict`，其中 E 显式性、U 未来效用、S 稳定性、C 置信度、R 复现频次、N 新颖性，Risk 为隐私/安全风险，Conflict 为与高权威记忆的冲突度；决策上：用户明说"记住"且不敏感则同步写入，得分 ≥0.75 自动晋升，0.45~0.75 进观察区，<0.45 仅留事件日志，密钥口令禁止写入普通记忆，Assistant 自行推测不进入高权威记忆 [1]。

**存储结构**：推荐"权威存储 + 派生索引"——权威记录含结构化字段、原文、来源引用、时间范围、状态与版本；派生索引含向量、BM25/FTS、实体关系、时间、标签与作用域索引 [1]。数据模型的关键字段包括 `scope`（用户/项目/组织/Agent 隔离）、`authority`、`confidence`、`importance`、`valid_from`/`valid_to`/`expires_at`、`status`（active/superseded/invalid/deleted）、`supersedes`、`embedding_version` [1]。这与 Zep 的双时态建模、MemoriesDB 在 PostgreSQL+pgvector 上"时间序列 + 向量 + 图"合一的主张方向一致 [9][10]。

**层级迁移**是另一条主线：MemoryOS 采用两阶段迁移，短期记忆先按 FIFO 进入中期存储，中期记忆再晋升到长期存储；MemoryBank 把重复的日常记录聚合成事件摘要并随经验累积精炼全局用户画像 [5]。统一框架把记忆操作归纳为三类：连接相关经验、整合碎片记忆（抽象/摘要）、跨层级转化 [5]。

**治理原则**（十条中较关键的几条）：可追溯（每条记忆知道来自哪条消息/工具/文件/时间点）、可更新（版本化而非永久保留错误）、有时间语义（区分"曾经如此/当前如此/计划未来如此"）、有作用域、有权威等级（用户明确表达 > Agent 推断；系统安全策略 > 普通记忆）、可删除、可评测（不只看召回率，还要测错误写入、过期、冲突、越权、投毒、Token 成本）、可迁移（向量模型/数据库/Runtime 可替换）、不能成为唯一真相（关键业务状态与实时外部事实由权威系统管理）[1]。

## 五、评测：基准已成型，但数字要打折

质量几乎完全用**端到端 QA 基准**打分（LoCoMo、LongMemEval、DMR、LoCoMo-Plus），而非组件级检索指标（recall@k、MRR、nDCG 等 IR 指标在主流记忆基准中并未被采用）[10]。

- **LoCoMo**（Snap Research, ACL 2024）：机器-人流水线生成带人格与时间事件图的对话，约 300 轮 / 9K token / 最多 35 个会话，题型含单跳、多跳、时序、常识、对抗，用字符串匹配 F1 打分。局限：公开评测集约 10 段对话，审计发现**约 6.4% 的答案键错误（99/1540）**，部分"多跳"题在单个会话内即可回答，评测 prompt 不一致曾导致 Zep 被重打分（84% → 58.44%）[10]。
- **LongMemEval**（ICLR 2025）：500 道题嵌入可自由扩展的聊天历史，分五项能力分别打分（信息抽取、多会话推理、时序推理、知识更新、拒绝作答）；发现商用助手在持续交互下准确率下降约 30%（30–60%）[10]。
- **DMR**：MemGPT 团队自建指标，规模小，Zep 与 MemGPT 都自报其成绩 [10]。
- **LoCoMo-Plus**（2026）：把 LoCoMo 扩展到"Level-2"认知记忆（因果、状态、目标、价值四类潜在约束），SOTA 分数从 LoCoMo 掉约 15–17 分（Mem0 在 GPT-4o 上 57.24 → 41.44）；但为单一来源、由作者自行提出且未被复现 [10]。

需要强调的是：**几乎所有头条准确率都是厂商自报且存在争议，缺少独立复现** [10]。

各系统的公开（自报）数字汇总如下：

| 系统 | 关键数字 | 来源性质 |
|---|---|---|
| Letta (MemGPT) | 74.0% LoCoMo（Filesystem），94.8% DMR | 自报 [9] |
| Mem0 | 66.9% LoCoMo（LLM 评分，"较 OpenAI Memory 相对提升 26%"），91% p95 延迟下降、>90% token 节省 | 厂商自报 [9][10] |
| Zep / Graphiti | 71.2% LongMemEval（全上下文基线 60.2%），DMR 94.8% vs MemGPT 93.4%；LongMemEval 最高 +18.5%、延迟约降 90% | 厂商自报，作者本人呼吁独立复现 [9][10] |
| Hindsight | 91.4% LongMemEval（已公开最高） | 自报 [9] |
| ChatGPT (OpenAI) | 52.9% LoCoMo | 自报/第三方汇总 [9] |
| Mastra (Observational Memory) | 95% LongMemEval（最高 OM 变体） | 自报 [9] |
| SuperMemory | 81.6% LongMemEval（GPT-4o） | 自报 [9] |

不同基准不可直接横向比较：LoCoMo 与 LongMemEval 的题型、历史长度、评分方式完全不同，同一系统在两套榜上的名次会大幅变化。文献层面还有多层级记忆架构的实验评估（如 MLMF 在 LOCCO 上报告更高的六期记忆保持率、LoCoMo 0.618），但属单篇实验结果 [11]。

## 六、选型建议与尚未解决的问题

**按需分层，不要一步到位。** 决策顺序应当是：先判断任务是否真的需要跨会话记忆（单次任务把窗口开大可能就够）[2]；确认需要后，优先补齐**情景记忆**（结论、决策、否决项、带时间戳可覆盖）[2]；知识型事实才交给向量/全文索引 [2]。

**最小可行版本（第一阶段）**：只做用户级与工作区级两类作用域；只做用户偏好、项目事实、Episode 三类记忆；支持显式记住/忘记/更正；会话结束后台提取；SQLite 作权威存储；FTS5 + 向量混合检索；带来源、时间、状态、权威字段；用户可查看/编辑/删除；写入审计；基础召回与越权测试。第二阶段再加时态冲突、自动 Consolidation、图关系、多 Agent 共享、Skill Candidate、离线评测、跨设备同步、企业级权限治理 [1]。

**落地策略矩阵**（节选）：用户明确偏好 → 会话内同步、SUPERSEDE、长期；用户更正 → 旧值失效新值生效；项目架构决策 → 版本化，直到新决策取代；临时计划 → 带时间区间、自动过期；会话摘要 → 增量合并、30~180 天；工具失败 → 追加 Episode、30~90 天；重复成功流程 → 多 Episode + Eval 通过后升为版本化 Skill；密钥密码 → 禁止写入普通记忆 [1]。写入时机上，"显式记住/忘记/更正"走同步保证用户可感知一致，"普通事实提取"走后台异步，"上下文压缩前"必须先提取候选记忆 [1]。

**Coding Agent 是记忆机制最成熟的落地场景**，且普遍把"确定性规则"与"自动学习记忆"分层处理 [3]：Claude Code 用人工维护的 CLAUDE.md 承载稳定规则 + Auto Memory 积累偏好与项目背景，并明确"避免重复保存可直接从代码推导的信息"；OpenAI Codex 的分工是"规则 → AGENTS.md，历史经验 → Memories，重复流程 → Skills，实时外部信息 → MCP/Tools"；Gemini CLI 提供显式 `save_memory` 工具写入 `GEMINI.md`，自动化弱但可控；GitHub Copilot 把事实关联到代码引用，并在**使用时重新验证引用在当前分支是否仍有效**（"记忆 + 代码证据 + 读取时验证"）；Cursor 则以 Rules 承载规则 [3]。

**仍未解决的问题**（公开资料层面的共识与空白）：
1. **检索延迟、灾难性遗忘、安全对齐**被综述列为生产级 Agent 待解的关键挑战，且"记忆+学习+进化"三支柱融合的生产系统仍处早期探索阶段 [8]。
2. **评测缺乏独立复现**：头条数字多为厂商自报，基准本身存在答案键错误与 prompt 不一致问题 [10]。
3. **多 Agent 共享记忆的治理**（权限、越权、投毒）在多数方案里仍不成熟，Agent 自管理记忆路线尤其如此 [1][3]。
4. **记忆写入本身是一种高风险权限**，需要 Policy、审计与敏感信息控制，但目前各产品差异很大 [1]。
5. 关于"情景记忆晋升为 Skill"的自动化闭环（离线聚类 + 评测 + 版本化回滚），公开的工程细节仍然有限，多数资料只给出概念性流程 [1][3]。
